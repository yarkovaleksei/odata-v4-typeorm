# Как участвовать

Спасибо за интерес к проекту. Здесь — только то, что касается совместной работы:
команды, окружение, отладка и структура кода описаны в
[docs/development.md](./docs/development.md), а границы поддержки OData —
в [docs/odata-support.md](./docs/odata-support.md).

## Сообщить о дефекте

Перед тем как заводить issue, загляните в [docs/audit.md](./docs/audit.md): там
шестнадцать разобранных дефектов с воспроизведением и статусом. Возможно, ваш случай уже
описан, а к нему есть обходной путь.

Проверьте по [docs/odata-support.md](./docs/odata-support.md), поддерживается ли
конструкция вообще. Библиотека сознательно отвергает то, чего не умеет: `400`
с `ODataUnsupportedError` — это не дефект, а заявленное поведение.

В issue нужны: OData-запрос целиком, сущности TypeORM (можно сокращённо), СУБД и её версия,
ожидаемый и фактический результат. Если удалось получить SQL — приложите его, это экономит
половину переписки. Шаблон предложит те же поля.

## Предложить изменение

1. Обсудите замысел в issue до того, как писать код, — особенно если он затрагивает
   генерацию SQL или публичный API. Большая часть работы разложена по этапам
   в [docs/roadmap.md](./docs/roadmap.md), и вероятно, для задачи уже есть номер `R-NN`.
2. Ветка от `master`, один PR — одно изменение.
3. Перед отправкой:

   ```bash
   yarn verify        # lint + формат + документация + тесты + сборка
   yarn db:up && yarn test:all   # если правили генерацию SQL
   ```

   Прогон на PostgreSQL и MySQL нужен не для галочки: половина исправленных дефектов
   (A-05, A-15, расхождения `div` и `round`) видна только на конкретной СУБД.

## Что ожидается от изменения

**Тесты.** Исправление дефекта сопровождается тестом, который без правки падает.
Новая возможность OData добавляется строкой в [`src/test/matrix/`](./src/test/matrix/)
и строкой в [docs/odata-support.md](./docs/odata-support.md) — матрица там исполняемая,
и запись «работает» должна быть подкреплена зелёным тестом на реальной БД.

**Ожидания пишутся по спецификации, а не по текущему поведению.** Упавший матричный
тест — это заявка на доработку, а не повод подогнать ожидание под реализацию.

**Никакого частичного выполнения.** Если конструкция не поддерживается — `ODataUnsupportedError`.
Молча выполнить запрос без части условий нельзя: именно так выглядели самые дорогие дефекты
проекта (A-11, A-12) — ответ `200` с неверными данными не ловится ни мониторингом,
ни клиентом.

**Документация правится вместе с кодом.** Она входит в контракт, и `yarn docs:check`
проверяет ссылки, якоря, примеры и упомянутые команды. Ломающее изменение попадает
в [CHANGELOG.md](./CHANGELOG.md), в раздел «Не выпущено».

**Комментарии объясняют «почему».** «Что» видно из кода; ценность имеет причина —
особенность СУБД, требование спецификации, обход чужого дефекта. Комментарии, сообщения
тестов и текст документации — на русском, как в существующем коде.

## Стиль

Формат и линтер настроены и проверяются в CI: `yarn format` и `yarn lint:fix`
приводят код в порядок. Ручного стиля держаться не нужно — достаточно не спорить
с этими двумя командами.

Сообщения коммитов — [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/)
с описанием на русском:

```
feat(filter): функции date и time
fix(security): не отдавать колонки select:false
test(db): прогон матрицы на PostgreSQL и MySQL
docs: уточнить план по фактическим замерам
```

Восклицательный знак (`feat!:`) отмечает ломающее изменение.
