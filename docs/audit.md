## 2. Что представляет собой проект

Компилятор OData v4 query options в запросы TypeORM. Форк `odata-v4-typeorm`; на момент
аудита был надстроен над двумя библиотеками JayStack — `odata-v4-parser` (строка → AST)
и `odata-v4-sql` (AST → фрагменты SQL через паттерн «посетитель»). Обе заменены своим кодом
при закрытии A-10.

Конвейер:

```
req.query
  │
  ├─ parseQueryParams ──────────── нормализация типов, отделение $search
  │
  ├─ queryToOdataString ────────── объект → query string
  │
  ├─ createQuery ───────────────── строка → AST → TypeOrmVisitor
  │                                 (where, select, orderby, parameters, includes)
  │
  └─ executeQueryByQueryBuilder ── SELECT / andWhere / setParameters
       ├─ processIncludes ──────── includes → LEFT JOIN
       ├─ processSearch ────────── $search → LIKE ... OR ...
       └─ getMany | getManyAndCount
```

Объём на момент первого аудита: 11 модулей, ~1000 строк рабочего кода, ~1700 строк тестов.
Сейчас: 56 файлов в `src/lib`, ~7000 строк рабочего кода и ~6100 строк тестов. Прибавка
пришлась на модуль `metadata`, матрицу совместимости и на собственный разбор OData, которым
заменены три неподдерживаемых пакета (A-10).

## 3. Дефекты

### A-01 · [ИСПРАВЛЕНО] Плейсхолдеры `contains`/`startswith`/`endswith` связываются с чужим параметром

**Критичность: высокая.** Запрос не падает — молча возвращает неверные строки.

`TypeOrmVisitor.VisitLiteral` пишет в SQL сразу именованный плейсхолдер `:pN`, а
`VisitMethodCallExpression` для LIKE-функций пишет позиционный `?`, рассчитывая на то,
что `asType()` его перенумерует. Но `Visitor.asOracleSql()` в `odata-v4-sql` не знает про
уже расставленные имена и нумерует найденные `?` подряд **с начала** `parameters`:

```js
this.where = this.where.replace(/\?/g, () => `:${keys.next().value}`);
```

Воспроизведение:

```js
createQuery("$filter=name eq 'x' and contains(title,'y')", { alias: 'u' });
// where  : "u.name = :p0 AND u.title like :p0"   ← должно быть :p1
// params : { p0: 'x', p1: '%y%' }
```

Сквозная проверка на SQLite (сущность `User`, есть строка `Alice / alice@example.com`):

```js
executeQuery(repo, { $filter: "name eq 'Alice' and contains(email,'alice')" }, { alias: 'User' });
// → { items: [], count: 0 }   ← ожидается одна строка
```

Дефект проявляется, когда в одном `$filter` есть и обычное сравнение, и LIKE-функция,
причём сравнение идёт **первым**. Обратный порядок работает случайно.

**Причина:** смешение двух форматов плейсхолдеров в одном классе.
**Решение:** в трёх ветках `contains` / `startswith` / `endswith` писать `` this.where += ` like :${name}` ``
вместо `' like ?'`. Тогда `asOracleSql()` не найдёт `?` и ничего не перенумерует.
**Затронуты тесты:** три теста в `TypeOrmVisitor.test.ts` фиксируют `like ?` как ожидаемое поведение
и должны быть переписаны на `like :p0`.

### A-02 · [ИСПРАВЛЕНО] `$expand` + фильтр/сортировка по той же связи → ошибка СУБД

**Критичность: высокая.** Запрос падает с ошибкой уровня БД, наружу уходит `500`.

`VisitExpand` даёт JOIN-алиас с позицией в строке (`posts8`), а `VisitPropertyPathExpression`
подставляет в WHERE чистое имя связи (`posts`).

```js
createQuery("$expand=posts&$filter=posts/title eq 'x'", { alias: 'u' });
// where : "posts.title = :p0"                      ← ссылка на алиас posts
// incl  : [{ nav: 'posts', alias: 'posts8', ... }] ← а JOIN сделан как posts8
```

```js
executeQuery(repo, { $expand: 'posts', $filter: "posts/title eq 'Alice first post'" }, { alias: 'User' });
// → SQLITE_ERROR: no such column: posts.title
```

То же самое для сортировки:

```js
executeQuery(repo, { $expand: 'posts', $orderby: 'posts/title desc' }, { alias: 'User' });
// → SQLITE_ERROR: no such column: posts.title
```

Без `$expand` те же запросы работают: тогда `VisitPropertyPathExpression` сам создаёт
«виртуальный» include с алиасом, равным имени связи, и алиасы совпадают.

**Причина:** две точки создания include используют разные схемы именования алиаса.
**Решение:** единая схема. Проще всего — в `VisitPropertyPathExpression` искать существующий
include по `navigationProperty` и, если он найден, писать в WHERE его `alias`, а не имя связи.

### A-03 · [ИСПРАВЛЕНО] `alias` обязан совпадать с именем сущности

**Критичность: средняя.** Ошибка явная и быстрая, но ограничение нигде не описано.

`executeQueryByQueryBuilder` ищет метаданные по алиасу: `inputQueryBuilder.connection.getMetadata(alias)`.
TypeORM трактует строку как имя класса сущности или имя таблицы, поэтому любой «человеческий»
короткий алиас ломает запрос:

```js
executeQuery(repo, { $top: '10' }, { alias: 'User' }); // OK
executeQuery(repo, { $top: '10' }, { alias: 'u' });    // Error: No metadata for "u" was found.
```

Ограничение особенно неочевидно в связке с `SelectQueryBuilder`: типовой код TypeORM
`createQueryBuilder('u')` здесь работать не будет.

**Решение:** брать метаданные из самого построителя — `inputQueryBuilder.expressionMap.mainAlias?.metadata`,
а `getMetadata(alias)` оставить только как запасной путь. Тогда алиас снова станет свободным.

### A-04 · [ИСПРАВЛЕНО] Повторный `$expand` одной связи даёт два JOIN

**Критичность: низкая.** Результат корректный, но запрос лишний раз джойнит таблицу.

Проверка на переиспользование в `VisitExpand` сравнивает `navigationProperty` дочернего посетителя
(`'posts'`, его выставляет базовый `VisitExpandItem`) с `expandPath` (`'posts8'`, путь + позиция).
Значения не совпадают никогда, поэтому дедупликация не работает:

```js
createQuery('$expand=posts($select=id),posts($select=title)', { alias: 'u' });
// incl: [{ nav: 'posts', alias: 'posts8'  }, { nav: 'posts', alias: 'posts26' }]
```

Занятно, что именно этот случай упомянут как поддерживаемый в комментарии к `queryToOdataString`.
Запрос отрабатывает, но выполняет два `LEFT JOIN` к одной таблице.

**Решение:** сравнивать с `item.value.path.raw`, а не с `expandPath`; при совпадении сливать
`$select` веток.

### A-05 · [ИСПРАВЛЕНО] `$search` ломается при нестандартной `namingStrategy`

**Критичность: средняя.** Проявляется только на проектах со snake_case-стратегией — но там сразу и полностью.

`processSearch` собирает условия из `column.propertyName` (имя свойства класса) и заключает
идентификаторы в двойные кавычки:

```js
conditions.push(`LOWER("${alias}"."${column}") LIKE LOWER(:textSearchValue)`);
```

Двойные кавычки отключают механизм TypeORM, который сопоставляет `alias.property` с реальным
именем колонки. При snake_case-стратегии свойство `firstName` живёт в колонке `first_name`:

```js
// DataSource({ namingStrategy: new SnakeNamingStrategy() })
executeQuery(repo, { $search: 'ann' }, { alias: 'Account' });
// → SQLITE_ERROR: no such column: Account.firstName
```

`$filter` при этом работает: там имена идут без кавычек и TypeORM их корректно транслирует.

Побочно, тот же фрагмент непереносим по цитированию: двойные кавычки — ANSI/PostgreSQL/SQLite,
но не MySQL/MariaDB (обратные кавычки).

**Решение:** использовать `column.databaseName` и `connection.driver.escape()` вместо
жёстко зашитых кавычек.

### A-06 · [ИСПРАВЛЕНО] Часть OData-функций не реализована и даёт битый SQL

**Критичность: средняя.** Вместо внятной ошибки — синтаксически неверный запрос.

`VisitMethodCallExpression` полностью перекрывает базовый метод, и функции, которых нет в его
`switch`, просто не дописывают ничего в `where`:

```js
createQuery("$filter=substring(name,1) eq 'x'", { alias: 'u' });
// where: " = :p0"     ← фрагмент SQL без левой части
```

Не реализованы: `substring`, `concat`, `replace`, `date`, `time`, `totaloffsetminutes`,
`mindatetime`, `maxdatetime`, `fractionalseconds`, `cast`, `isof`, геопространственные функции.

Дополнительно, среди реализованных есть непереносимые по СУБД:

| OData | Генерируется | PostgreSQL | MySQL | SQLite | MS SQL |
|---|---|---|---|---|---|
| `length` | `LEN(x)` | ❌ (`LENGTH`) | ❌ (`LENGTH`) | ❌ (`LENGTH`) | ✅ |
| `now` | `NOW()` | ✅ | ✅ | ❌ | ❌ |
| `indexof` | `INSTR(x, y) - 1` | ❌ (`POSITION`/`STRPOS`) | ✅ | ✅ | ❌ |
| `trim` | `TRIM(' ' FROM x)` | ✅ | ✅ | ❌ | ⚠️ (только 2022+) |

Ветвление по диалекту в `indexof` присутствует, но недостижимо: конструктор безусловно ставит
`SQLLang.Oracle`, поэтому `case SQLLang.MsSql` не выбирается никогда.

**Решение:** `default`-ветка с явной ошибкой `Unsupported OData function: <name>` вместо тихого
пропуска; выбор SQL-функции по `connection.options.type`, а не по `this.type`.

### A-11 · [ИСПРАВЛЕНО] Оператор `not` молча отбрасывается — фильтр перестаёт ограничивать выдачу

**Критичность: высокая** (корректность + доступ к данным). Обнаружено при прогоне матрицы операторов.

Базовый `Visitor` не реализует `VisitNotExpression`, а его метод `Visit` на неизвестный тип узла
не бросает ошибку, а печатает в `console.log` и продолжает:

```js
var visitor = this[`Visit${node.type}`];
if (visitor) visitor.call(this, node, context);
else console.log(`Unhandled node type: ${node.type}`, node);
```

Для `$filter=not (…)` весь фильтр целиком исчезает, и `where` остаётся нейтральным:

```js
createQuery('$filter=not (a eq 1)', { alias: 'u' });
// where: "1 = 1"     ← условие пропало полностью
// в stdout: "Unhandled node type: NotExpression Token { ... }"
```

Клиент, ограничивший выборку через `not`, получит **всю таблицу** вместо подмножества.
Ошибки при этом нет ни в ответе, ни в HTTP-коде — только строка в stdout процесса.

Тем же путём тихо теряются или ломаются:

| Запрос | Фактический `where` | Что происходит |
|---|---|---|
| `$filter=not (a eq 1)` | `1 = 1` | фильтр исчез, вернётся всё |
| `$filter=a add 1 eq 2` | `" = :p0"` | синтаксически битый SQL → ошибка СУБД |
| `$filter=a mod 2 eq 0` | `" = :p0"` | то же (`add`, `sub`, `mul`, `div`, `mod`) |
| `$filter=posts/any(p: …)` | `"u.posts"` | битый SQL (лямбда-операторы `any` / `all`) |
| `$filter=a in (1,2)` | — | `Unexpected character at 9` от парсера |

Отдельная проблема — сам способ сигнализации: `console.log` с дампом AST в stdout приложения.
В продакшене это шум в логах, а при `$filter` от недоверенного клиента — ещё и управляемый
клиентом объём вывода.

**Решение:** переопределить `Visit` (или добавить `VisitNotExpression` и арифметические узлы),
а на действительно неподдерживаемый узел бросать типизированную ошибку
`UnsupportedODataFeatureError`, которую HTTP-слой отдаст как `400`. Тихое игнорирование
условия в фильтре недопустимо ни при каких обстоятельствах.

### A-07 · [ИСПРАВЛЕНО] Клиентские ошибки отдаются как `500` с деталями БД

**Критичность: средняя** (безопасность/эксплуатация).

`ODataQueryMiddleware` обрабатывает любое исключение одинаково:

```js
res.status(500).json({ message: 'Internal server error.', error: { message: e.message } });
```

Следствия:

1. Синтаксически неверный `$filter` (ошибка клиента) отдаётся как `500`. Мониторинг будет
   считать это отказом сервиса, а клиент — не поймёт, что сам виноват.
2. `e.message` для `QueryFailedError` — это текст ошибки СУБД. Наружу уходит
   `SQLITE_ERROR: no such column: User.nope`, то есть имена таблиц и колонок.
   Через подбор `$filter=<имя> eq 1` схема БД перечисляется по одному полю за запрос.

**Решение:** классифицировать ошибку — парсер и `QueryFailedError` → `400` с нейтральным текстом,
всё остальное → `500`; детали писать только в лог.

### A-08 · [ИСПРАВЛЕНО] В npm-пакет попадают скомпилированные тесты

**Критичность: средняя** (публикация).

`tsconfig.build.json` исключает тесты так:

```json
"exclude": ["build", "node_modules", "examples", "src/**/*.(test|spec).ts"]
```

TypeScript поддерживает в путях только `*`, `?` и `**/` — групп с альтернативой `(a|b)` в его
glob-синтаксисе нет. Шаблон не совпадает ни с чем, и тесты компилируются вместе с библиотекой.
`.npmignore` их тоже не отсекает. Фактическое содержимое пакета (`npm pack --dry-run`):

```
105 файлов, 223 КБ
  build/src/lib/.../executeQueryByQueryBuilder.test.js
  build/src/lib/.../executeQueryByQueryBuilder.test.d.ts
  build/src/lib/.../parseQueryParams.test.js
  ...
```

Кроме размера, это тянет `@types/jest` в поставляемые `.d.ts`.

**Решение:** заменить на два корректных шаблона — `"src/**/*.test.ts"` и `"src/**/*.spec.ts"` —
и перейти с `.npmignore` на белый список `files: ["build/src/lib", "LICENSE", "README.md"]`.

### A-09 · [ИСПРАВЛЕНО] Необъявленная зависимость `odata-v4-literal`

**Критичность: средняя** (установка у потребителя).

`TypeOrmVisitor.ts` импортирует `odata-v4-literal`, которого нет ни в `dependencies`,
ни в `peerDependencies`. Сейчас работает только потому, что пакет подтягивается транзитивно
через `odata-v4-sql` и всплывает в плоский `node_modules`. При установке через pnpm
(строгая изоляция) или при смене внутренних зависимостей `odata-v4-sql` пакет упадёт
с `Cannot find module 'odata-v4-literal'`.

**Решение:** добавить в `dependencies` явно (`"odata-v4-literal": "^0.1.1"`).

### A-12 · [ИСПРАВЛЕНО] Колонки `select: false` возвращались клиенту на каждом запросе

**Критичность: высокая** (раскрытие данных). Обнаружено при разборе `TODO` в `processIncludes`.

`@Column({ select: false })` — способ TypeORM объявить «эта колонка не покидает сервер
по умолчанию»; типовое применение — хеши паролей и токены. Собственный `find()` в TypeORM
их скрывает.

Библиотека же строила список SELECT из **всех** невиртуальных колонок и передавала его
в `.select()`, тем самым явно переопределяя умолчание TypeORM:

```ts
rootSelect = metadata.nonVirtualColumns.map((x) => `${alias}.${x.propertyPath}`);
```

Воспроизведение на сущности `Acc { id, login, passwordHash: select false }`:

```js
executeQuery(repo, {}, { alias: 'Acc' });
// → { items: [{ id: 1, login: 'root', passwordHash: 'HASH' }], count: 1 }

await repo.find();
// → [{ id: 1, login: 'root' }]        ← TypeORM скрывает, библиотека — нет
```

Пять путей утечки, все проверены прогоном:

| Запрос | До | После |
|---|---|---|
| без параметров | `passwordHash` в ответе | скрыт |
| `$select=id,passwordHash` | значение в ответе | `400` |
| `$expand=tokens($select=id,secret)` | значение в ответе | `400` |
| `$filter=passwordHash eq '…'` | работает как оракул подбора | `400` |
| `$orderby=passwordHash` | оракул подбора | `400` |

Самый опасный — первый: утечка происходила **на каждом запросе, даже без единого параметра**.
`TODO` в коде описывал только третий случай.

`$filter` и `$orderby` не возвращают значение колонки, но по числу строк в ответе оно
подбирается, поэтому обращения к скрытой колонке отвергаются и там.

**Решение:** фильтр по `column.isSelect` в списке SELECT по умолчанию плюс проверка
`assertNoHiddenFields` по перечню путей, собранному посетителем.

### A-13 · [ИСПРАВЛЕНО] Пустой `alias` давал невалидный SQL с ведущей точкой

**Критичность: средняя.** Ломался ровно тот сценарий, ради которого существует `createFilter`.

`createFilter(expr, { alias: '' })` — документированный способ получить фрагмент `WHERE`
для «сырого» SQL без алиаса таблицы. Префикс колонки
приписывался безусловно, поэтому пустой алиас давал ведущую точку:

```js
createFilter('Id eq 42', { alias: '' }).where;
// → '.Id = :p0'     ← синтаксическая ошибка SQL
```

Дефект присутствовал с момента форка: в исходном `getIdentifier` при `this.alias === ''`
переменная `alias` получала значение `'.'`. При этом README и `docs/api.md` в обоих местах
обещали `'Id = :p0'` — то есть документация описывала поведение, которого никогда не было.

Не обнаруживался потому, что на `createFilter` не было ни одного теста (покрытие 31%).

**Решение:** префикс добавляется только при непустом алиасе; то же для имён JOIN-алиасов,
где пустой корень давал ведущее подчёркивание (`_author`).

### A-14 · [ИСПРАВЛЕНО] Сортировка связи перебивала корневой `$orderby`

**Критичность: средняя.** Обнаружено тестом на вложенную пагинацию.

Результат запроса с `LEFT JOIN` плоский, поэтому очерёдность выражений в `ORDER BY`
определяет и порядок корневых строк. `processIncludes` (он добавляет сортировки связей)
вызывался **до** применения корневого `$orderby`, из-за чего сортировка связи оказывалась
первой:

```sql
ORDER BY Author_books.id ASC, Author.id ASC   -- было
ORDER BY Author.id ASC, Author_books.id ASC   -- стало
```

Воспроизведение:

```js
executeQuery(repo, { $expand: 'books($orderby=id asc)', $orderby: 'id asc' }, { alias: 'Author' });
// порядок авторов: Barbara, Ada, Grace, Alan   ← корневой $orderby не работает
```

Barbara всплывала наверх, потому что книг у неё нет и `Author_books.id` для неё `NULL`,
а `NULL` в SQLite при `ASC` идёт первым. Отказа не происходило — просто неверный порядок,
что особенно неприятно в паре с `$top`: страница набиралась не из тех строк.

**Решение:** корневой `$orderby` применяется до `processIncludes`; сортировки связей
дописываются после и упорядочивают записи внутри каждого родителя.

### A-15 · [ИСПРАВЛЕНО] `$skip` без `$top` не работал на MySQL

**Критичность: высокая для MySQL.** Обнаружено первым же прогоном матрицы на реальной MySQL.

Конвейер вызывал `queryBuilder.skip($skip)` безусловно, в том числе с нулём. Для SQLite
и PostgreSQL это безобидно, а MySQL не умеет `OFFSET` без `LIMIT` — TypeORM заранее бросает
`OffsetWithoutLimitNotSupportedError`. В результате на MySQL падал **любой** запрос без `$top`,
то есть практически любой запрос вообще:

```js
executeQuery(repo, { $filter: "name eq 'Ada'" }, { alias: 'Author' });
// → OffsetWithoutLimitNotSupportedError: RDBMS does not support OFFSET without LIMIT
```

Два отдельных случая:

1. `$skip` не передан (нормализуется в `0`) — `skip(0)` всё равно выставлял `OFFSET 0`.
   Исправлено: `skip()` вызывается только при ненулевом смещении; нулевое смещение
   и его отсутствие — одно и то же.
2. `$skip=2` без `$top` — законный запрос OData, но MySQL требует `LIMIT`. Подставляется
   заведомо недостижимый лимит `Number.MAX_SAFE_INTEGER`: он умещается в 64-битное целое
   MySQL и на порядки больше любой реальной таблицы. Список драйверов, которым нужна
   такая подстраховка, повторяет условие внутри TypeORM (`mysql`, `mariadb`,
   `aurora-mysql`, `sap`, `spanner`).

Дефект не проявлялся три года, потому что тесты гонялись только на SQLite.

### A-16 · [ИСПРАВЛЕНО] Имена из настроек уезжали в документ `$metadata` без проверки

**Критичность: средняя.** Найдено повторным аудитом 2026-09-06: модуль `metadata` появился
после первого аудита и им не проверялся.

`createMetadataDocument` берёт три имени у вызывающего кода — `namespace`, `containerName`
и результат `entitySetName` — и подставляет их в документ как есть. Экранирование XML при
этом выполняется, поэтому файл остаётся синтаксически корректным, а вот CSDL — нет:
по спецификации (OData CSDL XML, раздел 4.1) это простые идентификаторы, в которых
недопустимы ни пробелы, ни точки, ни пустая строка.

```js
createMetadataDocument(ds, { entities: [Tag], entitySetName: () => 'not a name!' });
// <EntitySet Name="not a name!" EntityType="Default.Tag"/>   ← XML верен, CSDL невалиден

createMetadataDocument(ds, { entities: [Tag], entitySetName: () => '' });
// <EntitySet Name="" EntityType="Default.Tag"/>

createMetadataDocument(ds, { entities: [Tag], namespace: '1 bad ns' });
// <Schema … Namespace="1 bad ns">  и  EntityType="1 bad ns.Tag"
```

Отдельный и более опасный случай — **совпадение имён наборов**. Имя набора задаёт
вызывающий код, и две сущности легко получают одно и то же: достаточно, чтобы
`entitySetName` обрезал имя или приводил его к нижнему регистру.

```js
createMetadataDocument(ds, { entities: [Author, Book], entitySetName: () => 'Everything' });
// <EntitySet Name="Everything" EntityType="Default.Author"> …
// <EntitySet Name="Everything" EntityType="Default.Book">  …
// <NavigationPropertyBinding Path="books" Target="Everything"/>   ← куда именно, неизвестно
```

Для клиента имя набора — ещё и адрес. `ra-data-odata-server` складывает наборы в карту
по имени, поэтому один из двух молча вытесняет другой, а какой именно — зависит от порядка
разбора. Это ровно тот класс отказа, против которого написана вся остальная библиотека:
результат неверен, и никакого сигнала об этом нет.

Тем же путём проходил и повтор сущности в списке `entities` — документ получал два
одинаковых `EntityType` и два одинаковых `EntitySet`.

**Причина:** генератор проверял пригодность данных, пришедших из метаданных TypeORM
(ключи, встроенные сущности, таблицы связей), но не проверял ничего из того, что приходит
из настроек.

**Решение:** `namespace`, `containerName` и каждое имя набора сверяются с грамматикой
простого идентификатора CSDL до обхода сущностей; совпадение имён наборов отвергается
с указанием обеих сущностей; повтор в `entities` схлопывается — описать сущность дважды
нельзя ни в каком смысле.

### A-10 · [ИСПРАВЛЕНО] Устаревшие зависимости-основания

**Критичность: низкая, но стратегическая.**

| Пакет | Версия | Последний релиз | Статус |
|---|---|---|---|
| `odata-v4-parser` | 0.1.29 | ~2018 | не поддерживается |
| `odata-v4-sql` | 0.1.2 | ~2016 | не поддерживается |
| `odata-v4-literal` | 0.1.1 | ~2016 | не поддерживается, ещё и не объявлен |

Вся семантика разбора OData держится на неподдерживаемых пакетах. Практические последствия
уже видны: невнятные ошибки (`Error: Fail at 0` без позиции и контекста), отсутствие поддержки
`$apply` / `$compute` / лямбда-операторов (`any` / `all`), и невозможность починить A-01
в источнике — только обходом на своей стороне.

`odata-v4-server` (0.2.13) был в том же положении и убран из devDependencies вместе
с каталогом `src/example/`, которому только и требовался — см. наблюдение Н-11.

**Исправлено в 2.0.0 (R-18).** Все три пакета заменены своим кодом: разбор — `src/lib/odataParser`,
обход — `TypeOrmVisitor` (остаток базового класса перенесён внутрь), литералы — `src/lib/literal`.
Зависимостей времени выполнения у библиотеки не осталось вовсе.

Вендорить чужие исходники не стали: под флагами строгости этого проекта они дали 546 ошибок
компиляции, и на выходе получился бы большой массив кода, который никто здесь не понимает.
Свой парсер покрывает ровно транслируемое подмножество и оказался вчетверо короче. Замену
проверили сверкой: 254 запроса — вся матрица плюс отдельный набор — компилировались обоими
парсерами, и результат совпал везде, кроме одного случая. Этим случаем оказался приоритет
`not`: прежний парсер читал `not (X) and Y` как `not (X and Y)`, то есть ровно то расхождение
со спецификацией, ради которого задача и затевалась.

## 4. Наблюдения без дефекта

Не ошибки, но места, требующие решения.

**Н-01. `$count` включён по умолчанию.** ✅ Исправлено в 2.0.0. `parseQueryParams` при
отсутствии `$count` ставил `true`, тогда как OData v4 (раздел 11.2.5.5) требует `false`.
Следствий было два: форма ответа по умолчанию — `{ items, count }` вместо массива, и каждый
запрос делал лишнее обращение к БД (`getManyAndCount` вместо `getMany`). Отклонение считалось
осознанным и было документировано, но удобство одной формы ответа не окупает расхождения
со спецификацией в опции, которая эту форму и определяет: клиент, написанный по стандарту,
получал не то, что ожидал, и платил за это вторым запросом.

Теперь умолчание — `false`. Прежнее поведение возвращается явным `$count=true`. Изменение
ломающее, поэтому вынесено в мажорную версию.

**Н-02. Мёртвый код в `parseQueryParams`.** Строки 74–86 вычисляют `parsedQuery.$top`, который
безусловно перезаписывается следующей же строкой `parsedQuery.$top = toNumber(query.$top)`.
Удаляется без изменения поведения.

**Н-03. Мёртвое условие в `executeQueryByQueryBuilder`.** `Object.keys(odataQuery).length === 0`
не бывает истинным: `odataQuery` — экземпляр класса с собственными полями.

**Н-04. `$top` не валидируется.** `$top=-5` → `take(-5)`, TypeORM молча игнорирует лимит и
возвращает всё. `$top=999999999999` → падает уже парсер OData (`Fail at 0`). Верхней границы
страницы нет вовсе: клиент может запросить всю таблицу.

**Н-05. `strict` выключен в обоих tsconfig.** Нет `strictNullChecks`, `noImplicitAny`,
`noUnusedLocals`. Отсюда же 8 точечных `@ts-ignore` в `TypeOrmVisitor` и `mapToObject`.

Включён вместе с `noUncheckedIndexedAccess`, `noImplicitOverride`, `noUnusedLocals`
и `noUnusedParameters`. Библиотечный код прошёл `strict` сразу — переписанный посетитель
уже был типобезопасен. Остальные флаги дали три находки: мёртвое поле `isVirtual`
(выставлялось, но нигде не читалось), 17 отсутствующих `override` (важно, когда наследуешься
от библиотеки 2016 года: без них смена сигнатуры в базовом классе прошла бы незамеченной)
и необъявленный инвариант арности функций OData — он держался на грамматике парсера,
теперь проверяется явно.

**Н-06. Prettier настроен, но не установлен.** В корне лежит `.prettierrc`, при этом `prettier`
отсутствует в `devDependencies`, скрипта `format` нет, и CI формат не проверяет.

Исправлено: пакет установлен, `yarn format:check` стоит в CI. Из проверки исключена
документация — Prettier переносил бы в ней прозу и переверстывал таблицы; её целостность
проверяет отдельный шаг `yarn docs:check`.

**Н-07. Пробел в тестовом покрытии.** 112 тестов зелёные, но:
основной тест `executeQueryByQueryBuilder.test.ts` работает на моке QueryBuilder и проверяет
факт вызова методов, а не итоговый SQL; на реальной БД исполняются только два теста
(`executeQuery.test.ts`). Ни один из дефектов A-01…A-06 текущими тестами не ловится —
для A-01 тесты даже фиксируют дефектное поведение (`like ?`) как ожидаемое.
Покрытие не измеряется (`collectCoverage` не настроен).

Исправлено: 731 тест, весь набор исполняется на SQLite, PostgreSQL и MySQL; 96.8% строк.
Покрытие измеряется командой `yarn test:coverage`, пороги проверяются в CI — глобальный
и отдельно пофайловый, иначе новый файл вовсе без тестов почти не сдвигает средние цифры
и проходит незамеченным.

**Н-11. Мёртвая обвязка примера.** Вокруг `src/example/sql.ts` скопились файлы, которые
никто не использовал:

| Файл | Что это было |
|---|---|
| `config/default.json` | параметры подключения для пакета `config`; `"password": "***"` выглядел как вырезанный секрет |
| `src/example/world.sql` | 194 КБ, PostgreSQL-порт демо-базы «World» со своим уведомлением об авторских правах |

Ни один не загружался автоматически, в npm-пакет оба не попадали, а сам пример ничем
не запускался — из-за чего годами оставался нерабочим незамеченным: `parameters` это `Map`,
а код обращался к `.length` и `.concat` и подставлял `:pN` туда, где `pg` ждёт `$1`.

Каталог `src/example/` удалён целиком. Разбор показал, что уникального в нём была одна
функция — переходник от именованных плейсхолдеров `:pN` к позиционным `$n`; всё остальное
дублировало `docs/recipes.md` и тесты `from()`. Переходник перенесён в рецепты, где его
прочитают, а протухнуть он уже не может.

Из devDependencies убраны `config`, `@types/config` и `odata-v4-server` — было 20 пакетов,
стало 17.

**Н-08. `.npmrc` содержит строку-заглушку.** Последняя строка файла — `//SECRET`.
Секрета там нет, но конструкция похожа на обрезанную строку авторизации реестра
(`//registry.npmjs.org/:_authToken=...`). Стоит убрать, чтобы не пугать читателя и линтеры секретов.

**Н-09. Пример сервера использует API TypeORM 0.2.** `examples/server/src/server.ts` был построен
на `getConnection()` / `getRepository()` — глобальном API, объявленном устаревшим в 0.3.

Проверка показала, что дело хуже: сервер **вообще не компилировался**. У него был свой
`package.json` с собственным `typeorm`, и две копии библиотеки в одном проекте давали
несовместимые номинальные типы, а импорт библиотеки соседним путём нарушал `rootDir`.
Как и `src/example/sql.ts`, он годами оставался сломанным, потому что ничто его не собирало.

Переписан на `DataSource`, отдельная установка убрана (живёт на зависимостях корня),
добавлен интерактивный конструктор запросов, а типы теперь проверяются в CI.

**Н-10. `package.json` без современных полей.** Нет `exports`, `files`, `engines`, `sideEffects`.
`typings` указывает на `build/src/lib` без расширения — работает, но нестандартно.
ESM-потребители получат пакет только через CJS-интероп.

## 5. Безопасность

**Что закрыто.**

- Значения из `$filter` не попадают в SQL: `VisitLiteral` при `useParameters` (включён по умолчанию)
  кладёт их в `parameters`, в строку идёт плейсхолдер. Проверено:
  `$search="'; DROP TABLE user; --"` отрабатывает как обычный поиск подстроки и данные не трогает.
- `$search` целиком параметризован (`:textSearchValue`, `:numberSearchValue`).
- Имена полей и связей приходят из грамматики `odata-v4-parser`, произвольную строку туда
  не подставить.

**Что закрыто с тех пор.**

1. **Утечка схемы БД через сообщения об ошибках** (A-07). Наружу уходит нейтральный текст,
   полное сообщение пишется в лог. Раскрытие включается явно через `exposeErrors`.
2. **Ограничение выбираемых полей и связей.** Появились `allowedFields` и `allowedExpands`.
   Перечень затронутых путей собирает сам посетитель во время обхода AST, поэтому проверка
   ловит и поля внутри функций (`contains(bio,'x')`), которые разбор строк пропустил бы.
3. **Верхняя граница страницы.** Появился `maxTop`; отрицательные `$top` / `$skip` отвергаются
   как `400`, а не игнорируются молча.

4. **Колонки `@Column({ select: false })`** больше не покидают сервер ни по одному пути —
   ни в выборке по умолчанию, ни через `$select`, `$filter` или `$orderby` (A-12).

**Что открыто.**

1. **Белые списки не включены по умолчанию.** Без `allowedFields` / `allowedExpands` клиент
   по-прежнему видит любое поле сущности, кроме помеченных `select: false`. Это осознанный
   компромисс совместимости, но для публичного API списки задавать обязательно.
2. **`$search` — последовательное сканирование.** `LIKE '%…%'` по всем текстовым колонкам
   не использует индексы; на больших таблицах это рычаг для нагрузки.

Отдельно: `TypeOrmVisitor.from(table)` подставляет имя таблицы в SQL без экранирования.
В публичном сценарии оно приходит из кода, а не от клиента, но метод стоит пометить как
не предназначенный для пользовательского ввода (сделано в комментарии).

A-11 и A-01 объединяла общая черта: **отказ без сигнала**. Запрос не падал, HTTP-код `200`,
в ответе — данные, только не те, что запросили. Это опаснее явной ошибки, потому что
не диагностируется ни мониторингом, ни клиентом. Поэтому они шли первыми, и теперь на их месте
действует правило: непереводимая конструкция даёт `ODataUnsupportedError`, а не тихий пропуск.

Из наблюдений закрыты Н-02 и Н-03 (мёртвый код удалён вместе с переписыванием `$top`)
и часть Н-05 (`@ts-ignore` в посетителе устранены типизацией целевого поля).
`$top=0` приведён к спецификации: теперь это пустая страница, а не «лимита нет».
