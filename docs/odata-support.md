# Поддержка OData v4

Что библиотека умеет на самом деле. Таблицы построены по фактическому поведению
(проверено запуском на реальной БД, не выведено из кода) и покрыты матричными тестами
в [`src/test/matrix/`](../src/test/matrix/) — если строка таблицы говорит «работает»,
за ней стоит зелёный тест. Легенда:

- ✅ работает;
- ⚠️ работает с оговоркой — читайте примечание;
- ❌ не работает: молча игнорируется, даёт битый SQL или ошибку парсера.

## Системные query options

| Опция | Статус | Примечание |
|---|---|---|
| `$filter` | ✅ | Сравнения, логика, `not`, арифметика, функции, `in`, лямбды `any` / `all` |
| `$select` | ✅ | Включая `Связь/Поле` — связь при необходимости присоединяется автоматически |
| `$orderby` | ✅ | По полям корня и по полям связей, в том числе одновременно с `$expand` |
| `$top` | ✅ | `$top=0` даёт пустую страницу; отрицательный отвергается; потолок задаётся опцией `maxTop` |
| `$skip` | ✅ | |
| `$count` | ✅ | Выключен по умолчанию, как требует спецификация. Меняет форму ответа, см. ниже |
| `$expand` | ✅ | Вложенные `$select` / `$filter` / `$orderby` / `$expand` — да. Вложенные `$top` / `$skip` вырезают страницу в SQL, см. ниже |
| `$search` | ✅ | Грамматика разбирается целиком: `"фраза" AND NOT слово`, скобки. Поиск по полям связей и полнотекстовый режим — опциями |
| `$apply` | ❌ | `Fail at 0` от парсера |
| `$compute` | ❌ | `Fail at 0` от парсера |
| `$format` | ❌ | Ответ всегда JSON |
| `$levels` | ❌ | |
| `$skiptoken` | ❌ | Пагинация по токену не поддерживается, только `$top` / `$skip` |

### Форма ответа и `$count`

`$count` — единственная опция, которая меняет не содержимое ответа, а его форму.

| Запрос | Ответ |
|---|---|
| `GET /api/users` | `[...]` |
| `GET /api/users?$count=false` | `[...]` |
| `GET /api/users?$count=true` | `{ "items": [...], "count": 42 }` |

Отсутствующий `$count` эквивалентен `$count=false` — так требует OData v4,
раздел 11.2.5.5. Истиной считается только литерал `true` (в любом регистре); `1`, `yes`
и прочее дают `false`, чтобы поведение не зависело от способа сериализации.

`count` — общее число строк по текущим фильтрам, **без учёта** `$top` и `$skip`. Отсюда
приём «узнать количество, не вытягивая строки»: `$top=0&$count=true` вернёт
`{ "items": [], "count": 42 }`.

Практические следствия:

- возвращаемый тип — объединение `T[] | GetManyResponse<T>`, его нужно сужать на стороне вызова;
- с `$count=true` запрос делает **два** обращения к БД (`getManyAndCount`), поэтому
  включайте счётчик только там, где он действительно нужен.

> **Изменение в 2.0.0.** До этой версии `$count` был включён по умолчанию — отступление
> от спецификации, из-за которого каждый запрос возвращал объект и тянул лишний
> `COUNT(*)`. Теперь умолчание приведено к спецификации; чтобы вернуть прежнюю форму
> ответа, передавайте `$count=true` явно.

## Операторы `$filter`

### Сравнение

| Оператор | SQL | Статус |
|---|---|---|
| `eq` | `=` (или `IS NULL` для `null`) | ✅ |
| `ne` | `<>` (или `IS NOT NULL`) | ✅ |
| `gt` | `>` | ✅ |
| `ge` | `>=` | ✅ |
| `lt` | `<` | ✅ |
| `le` | `<=` | ✅ |
| `in` | `IN (…)` | ✅ Список значений в скобках: `age in (30, 40)` |
| `has` | — | ❌ |

### Логика

| Оператор | Статус | Примечание |
|---|---|---|
| `and` | ✅ | |
| `or` | ✅ | |
| `( )` | ✅ | `(a eq 1 or b eq 2) and c eq 3` → `(u.a = :p0 OR u.b = :p1) AND u.c = :p2` |
| `not` | ✅ | Приоритет по спецификации: `not (X) and Y` читается как `(not X) and Y` |

#### Приоритет `not`

`not` связывает сильнее, чем `and` и `or`, как и требует спецификация (раздел 5.1.1.9):

```bash
# (not X) and Y — отрицание относится только к первому условию
$filter=not (name eq 'Ada') and age gt 40
```

> **Изменение в 2.0.0.** До этой версии разбор шёл через `odata-v4-parser` 0.1.29, который
> следовал не таблице приоритетов, а ABNF того же документа: там `notExpr = 'not' RWS
> boolCommonExpr`, то есть отрицание поглощало и `and`, и `or`. Запрос выше читался как
> `not (X and Y)` и возвращал другое множество строк. Обходились внешними скобками —
> `(not (name eq 'Ada')) and age gt 40`; эта запись по-прежнему работает и означает то же самое.
> Подробности перехода на свой парсер — в [roadmap.md](./roadmap.md), задача R-18.

### Арифметика

| Оператор | SQL | Статус |
|---|---|---|
| `add` | `+` | ✅ |
| `sub` | `-` | ✅ |
| `mul` | `*` | ✅ |
| `div` | `/` | ✅ |
| `mod` | `%` | ✅ |
| унарный `-` | `-` | ✅ |
| `( )` в арифметике | `( )` | ✅ |

`div` над целыми — целочисленное деление (`41 div 2` = 20), как и требует спецификация
(раздел 5.1.1.7).

### Лямбда-операторы

`any` и `all` работают (OData v4, раздел 5.1.1.13):

```bash
$filter=books/any(b: b/pages gt 400)      # есть хотя бы одна книга длиннее 400 страниц
$filter=books/all(b: b/pages gt 200)      # все книги длиннее 200 страниц
$filter=books/any()                       # книги вообще есть
$filter=books/reviews/any(r: r/score eq 5)          # путь до коллекции может быть составным
$filter=books/any(b: b/reviews/any(r: r/score eq 5)) # и лямбды вкладываются друг в друга
```

Оба разворачиваются в коррелированный подзапрос, а не в соединение:

```sql
-- books/any(b: b/pages gt 400)
EXISTS (SELECT 1 FROM "book" "Author_books_b"
         WHERE "Author_books_b"."author_id" = "Author"."id" AND ("Author_books_b"."pages" > :p0))
```

Это принципиально: `JOIN` с коллекцией размножает корневые строки, и автор с тремя
подходящими книгами вернулся бы трижды, а `$top=10` отдал бы не десять авторов.
Именно поэтому фильтр по пути связи (`$filter=books/title eq 'x'`) — не замена `any`:
он даёт `LEFT JOIN`, и строки корня дублируются.

`all` вычисляется как `NOT EXISTS` с отрицанием условия, и потому правильно отвечает
на пустой коллекции: «все элементы удовлетворяют условию» истинно, когда элементов нет.

**Ограничения:**

| Что | Почему |
|---|---|
| Путь через связь внутри тела: `books/any(b: b/author/name eq 'Ada')` | Потребовал бы ещё одного соединения внутри подзапроса. Тот же смысл выражается вложенной лямбдой, которая поддержана. Запрос отвергается `ODataUnsupportedError`, а не выполняется частично |
| Лямбда при прямом вызове `createFilter` без метаданных | Имя таблицы взять неоткуда — компилятор OData знает только имена свойств. Через `executeQuery` метаданные подставляются сами |

**Про `NULL`.** Если условие для строки не определено (сравнение с `NULL`), такая строка
не попадает ни в `EXISTS`, ни в `NOT EXISTS` — то есть для `all` считается подходящей.
Это трёхзначная логика SQL, и библиотека её не переопределяет: запрос, написанный руками,
повёл бы себя так же.

SQL подбирается под конкретную СУБД: `executeQuery` берёт диалект из подключения TypeORM,
при прямом вызове `createQuery` / `createFilter` его можно передать опцией `dialect`.
Незнакомый драйвер сводится к ANSI.

| Функция | ANSI / PostgreSQL | MySQL | SQLite | MS SQL | Статус |
|---|---|---|---|---|---|
| `contains(f,'x')` | `f LIKE :p` | ← | ← | ← | ✅ |
| `startswith(f,'x')` | `f LIKE :p` | ← | ← | ← | ✅ |
| `endswith(f,'x')` | `f LIKE :p` | ← | ← | ← | ✅ |
| `tolower(f)` | `LOWER(f)` | ← | ← | ← | ✅ |
| `toupper(f)` | `UPPER(f)` | ← | ← | ← | ✅ |
| `trim(f)` | `TRIM(f)` | ← | ← | ← | ✅ |
| `round(f)` | `ROUND(f)` | ← | ← | ← | ✅ |
| `floor(f)` | `FLOOR(f)` | ← | ← | ← | ✅ |
| `length(f)` | `LENGTH(f)` | ← | ← | `LEN(f)` | ✅ |
| `ceiling(f)` | `CEIL(f)` | ← | ← | `CEILING(f)` | ✅ |
| `indexof(f,'x')` | `POSITION('x' IN f) - 1` | `INSTR(f,'x') - 1` | `INSTR(f,'x') - 1` | `CHARINDEX('x',f) - 1` | ✅ |
| `substring(f,n[,l])` | `SUBSTR(f, n + 1[, l])` | ← | ← | `SUBSTRING(f, n + 1, l)` | ✅ |
| `concat(a,b)` | `(a \|\| b)` | `CONCAT(a,b)` | `(a \|\| b)` | `CONCAT(a,b)` | ✅ |
| `year/month/day(f)` | `EXTRACT(YEAR FROM f)` | ← | `CAST(strftime('%Y',f) AS INTEGER)` | `DATEPART(year,f)` | ✅ |
| `hour/minute/second(f)` | `EXTRACT(HOUR FROM f)` | ← | `CAST(strftime('%H',f) AS INTEGER)` | `DATEPART(hour,f)` | ✅ |

## `$expand`

| Возможность | Статус | Пример |
|---|---|---|
| Простая связь | ✅ | `$expand=posts` |
| Несколько связей | ✅ | `$expand=posts,profile` |
| Вложенный `$select` | ✅ | `$expand=posts($select=id,title)` |
| Вложенный `$filter` | ✅ | `$expand=posts($filter=title eq 'x')` — фильтр попадёт в `ON`, а не в `WHERE` |
| Вложенный `$orderby` | ✅ | `$expand=posts($orderby=id desc)` |
| Вложенный `$expand` | ✅ | `$expand=posts($expand=comments)` |
| Вложенный `$top` / `$skip` | ⚠️ | Работает; срез делается после запроса, не в SQL — см. ниже |
| Вложенный `$count` | ❌ | |
| `$expand` + `$filter` по той же связи | ✅ | `$expand=author&$filter=author/name eq 'Ada'` |
| `$expand` + `$orderby` по той же связи | ✅ | `$expand=author&$orderby=author/name asc` |
| Повторный `$expand` одной связи | ✅ | Ветки объединяются в один `LEFT JOIN` с общим списком колонок |
| Фильтр по связи без `$expand` | ✅ | JOIN создаётся автоматически, колонки связи не выбираются |

Все JOIN — `LEFT`: `$expand` не отсеивает сущности без связанных записей.

**Алиасы JOIN** строятся по пути связи: `Author` → `Author_books` → `Author_books_reviews`.
Схема детерминированная, поэтому `$expand` и `$filter` по одной связи всегда приходят
к одному имени и к одному JOIN.

**Сортировка.** Корневой `$orderby` главнее сортировки связи: результат с `LEFT JOIN`
плоский, и если бы `ORDER BY` начинался с поля связи, родители без связанных записей
всплывали бы наверх (у них `NULL`).

### Вложенные `$top` и `$skip`

```bash
GET /api/authors?$expand=books($orderby=id desc;$top=1)   # по одной последней книге на автора
```

Ограничить число связанных строк на каждого родителя обычным `LIMIT` нельзя: результат
с `LEFT JOIN` плоский, и `LIMIT` действует на него целиком, а не на группу строк одного
родителя. Поэтому к условию соединения дописывается подзапрос с оконной функцией
`ROW_NUMBER() OVER (PARTITION BY <ключ родителя> ORDER BY <вложенный $orderby>)`,
и из базы поднимается только запрошенная страница.

Первичный ключ связи дописывается в сортировку окна: без него порядок строк с одинаковым
значением ключа не определён, и соседние страницы могли бы пересекаться или терять записи.

**Где срез по-прежнему делается после запроса** (результат тот же, из базы поднимаются
все связанные строки):

| Случай | Почему |
|---|---|
| MySQL и MariaDB | Считают окно после того, как протолкнут внешнее условие внутрь подзапроса: номер строки всегда получается первым, и `$top` молча перестал бы действовать. Проверено на `mysql:8.4` во всех формах записи условия |
| Незнакомый драйвер | Оконных функций может не быть вовсе |
| `$expand=books($orderby=category/name)` | Сортировка по соседней связи: её алиаса в подзапросе не существует |
| `nestedPaginationInSql: false` | Перенос отключён явно |

Отключить перенос можно опцией [`nestedPaginationInSql`](./api.md#executequery) — это нужно
на СУБД без оконных функций, которую библиотека не распознала (MySQL 5.7, MariaDB 10.1;
обе сняты с поддержки), либо при неудачном плане запроса на конкретных данных.

## `$search`

Реализован собственным кодом: `odata-v4-parser` грамматику `$search` не разбирает.

### Грамматика

Поддержана целиком (OData v4, раздел 5.1.7):

| Запись | Значение |
|---|---|
| `$search=ada` | слово |
| `$search=ada lovelace` | оба слова — пробел означает `AND` |
| `$search=ada AND lovelace` | то же самое явно |
| `$search=ada OR grace` | любое из слов |
| `$search=NOT ada` | строки, где слова нет |
| `$search="ada lovelace"` | фраза целиком, вместе с пробелом |
| `$search=(ada OR grace) hopper` | скобки меняют приоритет |

Приоритет: `NOT` сильнее `AND`, `AND` сильнее `OR`. Операторы распознаются **только
в верхнем регистре** — так требует грамматика, иначе `$search=black and white` нельзя было бы
найти как есть. Синтаксическая ошибка (незакрытая кавычка или скобка, оператор без операнда)
даёт `400`, а не поиск по строке как она есть.

### Где искать

По умолчанию — все скалярные колонки корневой сущности. Опция
[`searchFields`](./api.md#executequery) сужает набор и принимает пути через связи:

```ts
executeQuery(repo, req.query, { alias: 'Book', searchFields: ['title', 'author/name'] });
```

Поле связи компилируется в `EXISTS (SELECT 1 FROM …)`, а не в `JOIN`: соединение
с коллекцией размножило бы корневые строки, и `$top` начал бы возвращать не то число записей.
Работают все виды связей, включая «многие ко многим» и цепочки вида `books/reviews/text`.

### Как сравнивать

| Режим | SQL | Что находит |
|---|---|---|
| `'like'` (по умолчанию) | `LOWER(col) LIKE '%…%' ESCAPE '!'` | подстроку, в том числе внутри слова; индексы не используются |
| `'fulltext'` | `to_tsvector @@ plainto_tsquery` (PostgreSQL), `MATCH … AGAINST` (MySQL) | слова целиком, с учётом словоформ; опирается на индекс |

Режим переключается опцией [`searchMode`](./api.md#executequery), язык словоформ
PostgreSQL — `searchLanguage`. На SQLite и MS SQL режим `'fulltext'` молча остаётся `'like'`:
там полнотекстовый поиск требует отдельной виртуальной таблицы или каталога, и падать
на этом различии код не должен. **В MySQL колонка обязана входить в индекс `FULLTEXT`**,
иначе СУБД отвергнет запрос.

Структуру выражения в обоих режимах разбирает сама библиотека, а значение терма
обезвреживается, поэтому `$search` ведёт себя одинаково на всех СУБД, а `-слово`
не превращается в оператор булева режима MySQL.

`%` и `_` в строке поиска экранируются: `$search=50%` ищет именно «50%».

Каждое сравнение защищено проверкой `IS NOT NULL`: без неё `LIKE` по пустой колонке даёт
`NULL`, и `NOT` отбрасывал бы строки, которые обязан оставлять.

Имена колонок берутся из `databaseName` и экранируются драйвером, поэтому `$search`
работает и с нестандартной `namingStrategy` (snake_case), и на MySQL с его
обратными кавычками.

**Типы колонок, участвующие в поиске**

| Категория | Типы |
|---|---|
| Текстовые (LIKE) | `varchar`, `character varying`, `char`, `character`, `text`, `citext`, `nvarchar`, `nchar`, `ntext`, `tinytext`, `mediumtext`, `longtext`, `string` |
| Числовые (равенство) | `int`, `int2`, `int4`, `int8`, `smallint`, `integer`, `bigint`, `decimal`, `numeric`, `float`, `float4`, `float8`, `double`, `double precision`, `real`, `number` |

Осознанно исключены `uuid`, `json` / `jsonb`, `enum`, `date` / `timestamp`, `bytea` / `blob`:
`LIKE` по ним либо бессмысленен, либо роняет запрос на приведении типов.

**Производительность:** `LIKE '%…%'` не использует B-tree индексы — это последовательное
сканирование по всем текстовым колонкам. На больших таблицах ограничьте набор колонок
через `searchFields` и включите `searchMode: 'fulltext'`.

## Совместимость с СУБД

Библиотека не адаптирует SQL под конкретный драйвер, поэтому поведение зависит от того,
какие возможности вы используете.

| Возможность | PostgreSQL | MySQL | SQLite | MS SQL |
|---|---|---|---|---|
| `$filter` (сравнения, логика, арифметика) | ✅ | ✅ | ✅ | ✅ |
| `$select`, `$orderby`, `$top`, `$skip` | ✅ | ✅ | ✅ | ✅ |
| `$expand` | ✅ | ✅ | ✅ | ✅ |
| Строковые и числовые функции | ✅ | ✅ | ✅ | ✅ |
| Функции даты и времени | ✅ | ✅ | ✅ | ✅ |
| `$search` | ✅ | ✅ | ✅ | ✅ |
| `$search` + `namingStrategy` | ✅ | ✅ | ✅ | ✅ |

Матрица целиком прогоняется в CI на **SQLite, PostgreSQL и MySQL** — один и тот же набор
из 731 теста на каждой. MS SQL проверяется только на уровне генерируемого SQL
(юнит-тесты диалектов), живого прогона для него пока нет.

Локально:

```bash
yarn db:up          # поднять PostgreSQL и MySQL в контейнерах
yarn test:all       # прогнать матрицу на всех трёх
yarn db:down
```

**Расхождения, найденные прогоном** (свойства самих СУБД, а не дефекты трансляции):

| Что | Расхождение |
|---|---|
| `div` над целыми | PostgreSQL и SQLite дают целочисленное деление, как требует спецификация; в MySQL `/` возвращает дробное (`41 div 2` = 20.5). Подставить `DIV` безусловно нельзя — на дробных операндах он тоже усечёт, а типы операндов при трансляции неизвестны |
| `round` от «половинки» | SQLite округляет от нуля (`4.5` → 5), PostgreSQL для `float8` применяет банковское (`4.5` → 4) |
| `20 add 16` (два литерала) | PostgreSQL не выводит тип для выражения из двух безымянных плейсхолдеров: `operator is not unique: unknown + unknown`. Случай вырожденный — константу клиент вычисляет сам |

## Сводка «чего ждать»

**Работает:** `$filter` со сравнениями, логикой, `not`, арифметикой, `null` и всеми
перечисленными выше функциями в любых сочетаниях; `$select` (в том числе по связям);
`$orderby` по корню и по связям; `$top` / `$skip` / `$count`; `$expand` со вложенными
`$select` / `$filter` / `$orderby` / `$expand` и в сочетании с фильтрами по тем же связям;
`$search` на стандартных именах колонок.

**Требует внимания:** приоритет `not` относительно `and` (нужны явные скобки);
вложенные `$top` / `$skip` режут выборку после запроса, а не в SQL; `$count` меняет форму
ответа с массива на `{ items, count }`, поэтому возвращаемый тип нужно сужать; белые списки
полей и связей выключены по умолчанию — на публичном API их нужно задать.

**Не работает и отвергается с ошибкой:** `in`, `any` / `all`, `replace`, `cast`, `isof`,
`fractionalseconds`, `totalseconds`, `totaloffsetminutes`, `mindatetime`, `maxdatetime`,
геопространственные функции, `$apply`, `$compute`, `$levels`, `$skiptoken`.

Последние пять парсер разбирает, но осмысленной трансляции у них нет: `totalseconds` требует
типа `Edm.Duration`, `totaloffsetminutes` — колонки с часовым поясом, `mindatetime` /
`maxdatetime` упираются в разные границы диапазона дат у СУБД (MySQL `DATETIME` начинается
с 1000 года, PostgreSQL — с 4713 до н.э.). Подставлять приближение вместо них не стали:
тихое расхождение со спецификацией опаснее явного отказа.

Планы по закрытию пробелов — в [roadmap.md](./roadmap.md).
