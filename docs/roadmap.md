## Этап 1 · Молчаливые дефекты (релиз 1.0.4)

Наивысший приоритет: запрос возвращает `200` и неверные данные. Такое не диагностируется
ни мониторингом, ни клиентом.

### R-01 · Починить `not` и неизвестные узлы AST (A-11)

Сейчас `$filter=not (a eq 1)` теряет условие целиком и возвращает всю таблицу.

1. Реализовать `VisitNotExpression` в `TypeOrmVisitor`.
2. Переопределить `Visit`: на неизвестный тип узла бросать `UnsupportedODataFeatureError`
   вместо `console.log` с дампом AST.
3. Реализовать арифметику (`add`, `sub`, `mul`, `div`, `mod`) — она уже есть в грамматике
   парсера, нужна только трансляция.

**Оценка: 1.5 д. Риск: низкий** (сейчас эти узлы не работают вовсе, хуже не станет).
**Ломающее изменение:** запросы, которые раньше молча возвращали всё, начнут возвращать `400`.
Это и есть цель, но в CHANGELOG нужно указать явно.

### R-02 · Починить нумерацию плейсхолдеров LIKE (A-01)

В `VisitMethodCallExpression`, ветки `contains` / `startswith` / `endswith`:

```diff
- this.where += ' like ?';
+ this.where += ` like :${name}`;
```

После этого `asOracleSql()` не найдёт `?` и перенумеровывать будет нечего.

**Оценка: 0.5 д. Риск: низкий.**
**Требует правки тестов:** три теста в `TypeOrmVisitor.test.ts` фиксируют `like ?`.

### R-03 · Согласовать алиасы `$expand` и путей в фильтре (A-02)

В `VisitPropertyPathExpression` искать существующий include по `navigationProperty` и,
если он найден, писать в WHERE его `alias`, а не имя связи. Заодно закрывает A-04
(дублирующиеся JOIN) — если ту же проверку исправить в `VisitExpand`.

**Оценка: 1.5 д. Риск: средний** — затрагивает генерацию алиасов, нужен полный прогон R-00.1.

## Этап 3 · Практичность API (релиз 1.1.0)

### R-08 · Снять ограничение на `alias` (A-03)

Брать метаданные из построителя, а `getMetadata(alias)` оставить запасным путём:

```ts
const metadata =
  inputQueryBuilder.expressionMap.mainAlias?.metadata ??
  inputQueryBuilder.connection.getMetadata(alias);
```

После этого заработает привычный TypeORM-стиль `createQueryBuilder('u')`.

**Оценка: 0.5 д. Риск: низкий.**

### R-09 · Корректные коды ошибок и безопасные сообщения (A-07)

1. Ввести типы ошибок: `ODataParseError` (парсер), `ODataUnsupportedError` (R-01),
   и пробрасывать `QueryFailedError` из TypeORM отдельно.
2. В `ODataQueryMiddleware` маппинг: парсер и `QueryFailedError` → `400`, остальное → `500`.
3. Наружу отдавать нейтральный текст; `e.message` писать только в лог.
4. Добавить `settings.exposeErrors?: boolean` (по умолчанию `false`) для разработки.

**Оценка: 1 д. Риск: низкий.**
**Ломающее изменение:** форма тела ошибки и коды ответа.

### R-10 · Валидация и лимиты пагинации (Н-04)

- `$top < 0` → `400`;
- `$top` больше `settings.maxTop` → обрезать до `maxTop` (по умолчанию, скажем, 1000);
- `$skip < 0` → `400`;
- `$top` с дробной частью → `400` вместо тихого `parseInt`.

**Оценка: 0.5 д. Риск: низкий.**

### R-11 · Белый список полей и связей

Закрывает риск №2 из раздела «Безопасность» аудита: сейчас клиент через `$select` и `$expand`
достаёт любое поле сущности и проходит по любой связи.

```ts
executeQuery(repo, req.query, {
  alias: 'User',
  allowedFields: ['id', 'name', 'email'],
  allowedExpands: ['posts'],
});
```

Плюс учитывать `column.isSelect === false` в `processIncludes` (там стоит `TODO`).

**Оценка: 1.5 д. Риск: низкий** (опция, по умолчанию поведение прежнее).

### R-12 · Починить `$search` при нестандартной `namingStrategy` (A-05)

Использовать `column.databaseName` вместо `propertyName` и `connection.driver.escape()`
вместо жёстко зашитых двойных кавычек. Заодно чинит совместимость с MySQL.

**Оценка: 1 д. Риск: средний** — меняет генерируемый SQL, нужен прогон на трёх СУБД (R-00.4).

## Этап 4 · Полнота OData (релиз 1.2.0)

### R-13 · Диалект SQL по драйверу (A-06)

Выбирать SQL-функции по `connection.options.type`, а не по жёстко зашитому `SQLLang.Oracle`:
`LENGTH` вместо `LEN` для всех, кроме MS SQL; `POSITION` для PostgreSQL; `CURRENT_TIMESTAMP`
вместо `NOW()` там, где `NOW()` нет.

Тонкость: `SQLLang.Oracle` нужен для формата плейсхолдеров и трогать его нельзя —
диалект функций придётся вести отдельным полем.

**Оценка: 2 д. Риск: средний.**

### R-14 · Недостающие функции `$filter`

`substring`, `concat`, `replace`, `date`, `time`, `cast` — с учётом R-13.

**Оценка: 2 д. Риск: низкий.**

### R-15 · Оператор `in` и лямбды `any` / `all`

`in` не поддерживается уже парсером — потребуется либо предобработка строки
(`a in (1,2)` → `(a eq 1 or a eq 2)`), либо форк парсера. `any` / `all` транслируются
в `EXISTS (SELECT 1 FROM … WHERE …)`.

**Оценка: 3 д. Риск: высокий.**

### R-16 · Вложенная пагинация в `$expand`

`$expand=posts($top=2)` сейчас разбирается, но игнорируется. Честная реализация —
оконная функция `ROW_NUMBER() OVER (PARTITION BY …)` либо отдельный запрос на связь.

**Оценка: 3 д. Риск: высокий.**

### R-17 · Полноценный `$search`

Разбор грамматики OData (`"фраза"`, `AND` / `OR` / `NOT`), поиск по полям связей,
опциональная интеграция с полнотекстовым поиском СУБД (`tsvector` в PostgreSQL,
`MATCH AGAINST` в MySQL).

**Оценка: 4 д. Риск: средний.**

## Этап 5 · Фундамент (2.0.0)

### R-18 · Уйти от неподдерживаемых зависимостей (A-10)

`odata-v4-parser` (2018), `odata-v4-sql` (2016), `odata-v4-literal` (2016) не обновляются.
На них держится вся семантика разбора, и часть дефектов (A-01, A-11) — прямое следствие
чужих архитектурных решений.

Варианты:

| Вариант | Плюсы | Минусы |
|---|---|---|
| Форкнуть и вендорить обе библиотеки | Полный контроль, можно чинить в источнике | Своя поддержка парсера OData |
| Перейти на живой парсер (`@odata/parser`) | Активная поддержка | Другой AST — переписывать посетителя |
| Свой минимальный парсер поддерживаемого подмножества | Ровно то, что нужно; понятные ошибки | Самый дорогой вариант |

Рекомендация: **форк и вендоринг**. Пакеты небольшие, а необходимость чинить нумерацию
плейсхолдеров в источнике снимает разом A-01 и половину костылей в `TypeOrmVisitor`.

**Оценка: 5–10 д. Риск: высокий.**

### R-19 · Включить `strict` в TypeScript (Н-05)

`strict: true`, `noUnusedLocals`, `noImplicitOverride`; убрать 8 `@ts-ignore`
(большинство — из-за динамического `this[context.target]`, лечится типом
`target: 'where' | 'select' | 'orderby'` и явным свитчем).

**Оценка: 2 д. Риск: низкий** (компилятор всё покажет).

### R-20 · Поддержка ESM

Двойная сборка CJS + ESM через `exports`. Актуально по мере перехода экосистемы.

**Оценка: 1 д. Риск: средний.**

чем тянуть полную спецификацию.
