### ✅ R-01 · Починить `not` и неизвестные узлы AST (A-11)

3. Реализовать арифметику (`add`, `sub`, `mul`, `div`, `mod`) — она уже есть в грамматике
   парсера, нужна только трансляция.

### ✅ R-02 · Починить нумерацию плейсхолдеров LIKE (A-01)

В `VisitMethodCallExpression`, ветки `contains` / `startswith` / `endswith`:

```diff
- this.where += ' like ?';
+ this.where += ` like :${name}`;
```

После этого `asOracleSql()` не найдёт `?` и перенумеровывать будет нечего.

**Оценка: 0.5 д. Риск: низкий.**
**Требует правки тестов:** три теста в `TypeOrmVisitor.test.ts` фиксируют `like ?`.

### ✅ R-03 · Согласовать алиасы `$expand` и путей в фильтре (A-02)

В `VisitPropertyPathExpression` искать существующий include по `navigationProperty` и,
если он найден, писать в WHERE его `alias`, а не имя связи. Заодно закрывает A-04
(дублирующиеся JOIN) — если ту же проверку исправить в `VisitExpand`.

**Оценка: 1.5 д. Риск: средний** — затрагивает генерацию алиасов, нужен полный прогон R-00.1.

## Этап 4 · Полнота OData (релиз 1.2.0)

### ✅ R-13 · Диалект SQL по драйверу (A-06) — выполнено досрочно

Выбирать SQL-функции по `connection.options.type`, а не по жёстко зашитому `SQLLang.Oracle`:
`LENGTH` вместо `LEN` для всех, кроме MS SQL; `POSITION` для PostgreSQL; `CURRENT_TIMESTAMP`
вместо `NOW()` там, где `NOW()` нет.

Тонкость: `SQLLang.Oracle` нужен для формата плейсхолдеров и трогать его нельзя —
диалект функций придётся вести отдельным полем.

**Оценка: 2 д. Риск: средний.**

### ✅ R-14 · Недостающие функции `$filter`

Сделано: `substring` (2 и 3 аргумента), `concat`, `date`, `time`.

Попутно выяснилось, что `Literal.convert` превращает `Edm.TimeOfDay` в полный момент
времени (`08:00:00` → `1970-01-01T08:00:00.000Z`), тогда как `TIME(x)` во всех трёх СУБД
отдаёт `HH:MM:SS` — сравнение не сходилось. Время суток теперь привязывается строкой.

Сознательно не реализованы:

| Функция | Почему |
|---|---|
| `replace`, `cast` | не разбирает сам парсер (`Unexpected character`) — уходят в R-18 |
| `totalseconds` | нужна модель типа `Edm.Duration`, которой в библиотеке нет |
| `totaloffsetminutes` | нужна колонка с часовым поясом |
| `mindatetime`, `maxdatetime` | границы диапазона дат у СУБД разные (MySQL `DATETIME` — с 1000 года, PostgreSQL — с 4713 до н.э.); приближение молча расходилось бы со спецификацией |
| `fractionalseconds` | реализуемо, но громоздко и по-разному в каждой СУБД; спроса нет |

Все они отвергаются `ODataUnsupportedError`, а не выполняются частично.

### ⬜ R-15 · Оператор `in` и лямбды `any` / `all`

Обе возможности упираются в парсер, а не в генерацию SQL:

- `in` не разбирается вовсе (`Unexpected character at N`);
- `any` / `all` разбираются, но парсер **выбрасывает тело лямбды**: до библиотеки доходит
  обычный путь свойства без предиката. Проверено на AST.

Сейчас оба случая отвергаются с `ODataUnsupportedError` — то есть перестали быть тихой
потерей условия, но работать не начали. Для реализации нужен форк парсера (R-18),
после чего `any` / `all` транслируются в `EXISTS (SELECT 1 FROM … WHERE …)`,
а `in` — в SQL-оператор `IN`.

**Оценка: 3 д (после R-18). Риск: высокий.**

### ⚠️ R-16 · Вложенная пагинация в `$expand` — работает, но не в SQL

**Сделано:** `$expand=posts($top=2;$skip=1)` даёт правильный результат. Срез выполняется
модулем `applyNestedPagination` над деревом сущностей после запроса; вложенный `$orderby`
при этом отрабатывает в SQL, поэтому порядок к моменту среза уже верный.

Попутно найден и исправлен дефект A-14: сортировка связи попадала в `ORDER BY` раньше
корневой и перебивала её.

**Осталось:** перенести срез в SQL — оконная функция `ROW_NUMBER() OVER (PARTITION BY …)`
в подзапросе либо `LATERAL`-соединение. Сейчас из базы поднимаются все связанные строки,
что заметно на связях с тысячами записей на родителя. Это оптимизация, а не исправление:
результат уже корректен.

**Осталось: 2.5 д. Риск: средний** (затрагивает гидрацию сущностей в TypeORM).

### ⬜ R-17 · Полноценный `$search`

Разбор грамматики OData (`"фраза"`, `AND` / `OR` / `NOT`), поиск по полям связей,
опциональная интеграция с полнотекстовым поиском СУБД (`tsvector` в PostgreSQL,
`MATCH AGAINST` в MySQL).

**Оценка: 4 д. Риск: средний.**

### Уточнение по R-27

Формулировка «`&` в значении разрывает строку» оказалась неверной — проверено прогоном.
Фактическая картина по символам внутри строкового литерала `$filter=name eq '…'`:

| Символ | Результат | Причина |
|---|---|---|
| `&` `+` `=` `%` пробел | ✅ работает | парсер справляется даже без экранирования |
| `#` `?` | ❌ `ODataParseError` | `encodeURI` их не кодирует, парсер считает концом выражения |
| `'` | ❌ `ODataParseError` | по спецификации требует удвоения (`''`) — ответственность клиента |
| `/` | ❌ `ODataParseError` | ограничение парсера внутри литерала |

То есть чинить нужно только `#` и `?`, и это точечная правка кодирования значения,
а не переписывание функции. Приоритет ниже, чем предполагалось.

**Почему R-13 ушёл вперёд из этапа 4.** Матричные тесты показали, что без выбора SQL-функции
по диалекту `year()`, `length()`, `indexof()` и `now()` дают невалидный SQL на PostgreSQL
и SQLite — то есть строка «поддерживается» в матрице была бы неправдой. Диалектный слой
оказался не улучшением, а условием корректности уже заявленных возможностей.

**Минимально корректный пакет достигнут** (этапы 0–2): OData транслируется верно, ничего
не теряется молча, публикуется только библиотека, зависимости объявлены честно.

**Дальше по спросу** — этап 4: остаток функций `$filter` и вложенная пагинация в `$expand`.
Существенная его часть (`in`, `any`/`all`, `replace`, `cast`) недостижима без форка
парсера, то есть фактически относится к этапу 5.

Этапы 4–5 стоит планировать по спросу: если пользователям хватает текущего подмножества,
