## С чего начать

**Подключаю библиотеку в проект** → [recipes.md](./recipes.md) и рецепты своего фреймворка
([Express](./recipes-express.md), [NestJS](./recipes-nestjs.md)), затем
[odata-support.md](./odata-support.md), чтобы понимать границы.

**Ищу сигнатуру или тип** → [api.md](./api.md).

**Странное поведение, похоже на баг** → сверьтесь с [odata-support.md](./odata-support.md):
библиотека сознательно отвергает то, чего не умеет, и `400` там — заявленное поведение,
а не дефект. Если поведение расходится с документом — это баг, и о нём стоит завести issue
(как — в [CONTRIBUTING.md](../CONTRIBUTING.md)).

**Собираюсь дорабатывать пакет** → [development.md](./development.md) и
[architecture.md](./architecture.md), план задач — в [roadmap.md](./roadmap.md).

## Три вещи, которые удивляют в первую очередь

1. **Форма ответа зависит от `$count`.** Без него — массив, с `$count=true` —
   `{ items, count }`. Возвращаемый тип поэтому объединение, и его нужно сузить на
   стороне вызова. Подробности:
   [odata-support.md](./odata-support.md#форма-ответа-и-count).
2. **Умолчания у `$search` и `$expand` небезопасны для публичного API.** Без `searchFields`
   поиск идёт по всем колонкам корня, без `allowedFields` / `allowedExpands` клиент видит
   любое поле и любую связь. Подробности: [api.md](./api.md#executequery).
3. **Неподдерживаемое отвергается, а не игнорируется.** `isof`, `$apply`, приведение,
   которое может провалиться, и прочее
   дают клиентскую ошибку (в HTTP — 400): `ODataUnsupportedError`, если конструкцию
   принимает грамматика, иначе `ODataParseError`. Библиотека никогда не выполняет запрос
   частично и не возвращает молча не те данные.
